Prepared & locally tested

From your laptop
to someone else's browser.

Deployment means putting a ready-to-run version of StageFlow on your rented server, giving it a web address, and keeping it running when your laptop is off.

Where we are today: the setup files and operating instructions are in this repository, and we tested them on a disposable Linux server locally. We have not installed StageFlow on your actual VPS.

01 / The big picture

One server. Several small jobs.

Your VPS is a computer rented from Hostinger. Ubuntu is its operating system. StageFlow shares that computer with your other applications, so it gets its own files, passwords, private ports, and resource limits.

A

Getting the app onto the server

We build and test the code on Linux, copy a versioned release onto the VPS, update the database if needed, and start one API process.

This is currently an operator-run process. A Git push runs repository checks; it does not automatically deploy to the VPS.

B

Serving people after that

Visitors use your domain. Nginx delivers the website and forwards app requests to the API. The API uses private databases and recording storage.

systemd keeps the API running. You can disconnect your SSH session and turn off your laptop.

03 / Ship an update

A release is a controlled handover.

We prepare a new version alongside the old one. The database, passwords, and recordings live elsewhere, so replacing code preserves them. This profile uses a short maintenance window for the handover.

Step 1 / Prepare

Build a production version on Linux.

Install the exact dependency versions, compile the apps, and run the checks. The website's API and socket addresses are baked into its JavaScript during this build.

App stateExisting version can keep serving
Accounts & recordingsStay in persistent storage

The build command is pnpm build:production. A release includes compiled code and Linux runtime dependencies, with secrets kept separately.

04 / Keep your data

Code changes. Your recordings stay.

Three separate locations keep updates from overwriting the things you want to preserve.

Where things live on the VPS

Replaceable code/opt/stageflow/releases/<commit>/opt/stageflow/current → selected release

Each release has its own folder. “current” is a shortcut pointing to the selected version.

Protected configuration/etc/stageflow/

Database passwords, the login-token secret, and production settings. These are kept out of Git and release folders.

Persistent data/srv/stageflow/postgres/srv/stageflow/redis/srv/stageflow/media/srv/stageflow/backups

A dedicated 12 GiB filesystem protects the shared server from unbounded StageFlow data growth.

A recording has two pieces

PostgreSQL remembers who owns it, its visibility, and whether it is ready. Media storage holds the actual video files. A useful backup needs both from the same stopped-app snapshot.

The backup script makes that local pair and checksums it. Encrypting and copying it off the VPS is a separate operator step. A copy on the same disk does not protect against losing the VPS.

Resource limits are guardrails

The API and encoder together have a 1.5 GiB memory ceiling and 75% of one CPU core. The app allows one encoder, retains up to 1 GiB of media, and refuses new recording work when free space is too low.

These are proposed limits for a shared server. They do not prove how many simultaneous users your real VPS can support.

Nginx serves the website's build directory. Recordings stay private: the API checks access before serving HLS files, including owner-only replays.

05 / When things fail

A supervisor helps. A lock prevents confusion.

systemd starts the API, watches its process, and limits resource use. Redis holds an owner lock so two API processes cannot both control the same live rooms.

Graceful handover

The API gets time to close properly.

What the system does

systemd asks Node to stop. The app closes its live work, stops its encoder, and releases its owner lock. The stop budget is 45 seconds.

What remains

Accounts, room records, and completed recordings stay. Live memberships reset when the API starts again; an interrupted broadcast is not resumed.

What the operator does

Start one replacement and check database health, live readiness, and a protected replay before resuming the trial.

“Fence the old writer” means making certain the previous API, any manual copy, and any cloned old server cannot keep running. An operator can then remove only the exact old lock using the guarded recovery helper. The guide does not automate that decision.

A few read-only checks

These commands are for the VPS terminal after installation. The first health check asks PostgreSQL “are you reachable?”; the second asks whether live Redis is ready. 

sudo systemctl status stageflow.service
curl --fail http://127.0.0.1:4100/api/health
curl --fail http://127.0.0.1:4100/api/health/live
sudo journalctl --namespace=stageflow -u stageflow.service -n 50 --no-pager

Health checks run about every minute. Alerts currently write to the local journal; sending notifications to you still needs an external monitoring connection.

06 / Before going live

Prepared locally. Verified on the VPS next.

The current nginx template admits only requests from the server itself. Opening access is a deliberate later step, beginning with invited testers.

Already prepared and tested locally

  • Production builds and compiled startup/migration commands.
  • Linux services, encrypted test connections, live sockets, and recording.
  • Crash refusal, guarded recovery, disk alerts, and resource limits.
  • Backup/restore with a decoded private replay and another account denied.

Still needed for the real host

  • Inventory: installed OS, free resources, existing apps, and safe private ports.
  • A real domain: DNS, a trusted certificate, and tested certificate renewal.
  • Operations: external alerts, encrypted off-host backups, and a timed restore.
  • Real-world testing: shared-VPS load, remote TURN connectivity, browsers, and physical audio/video.

TURN is a relay that helps speakers behind difficult networks connect. The profile leaves it unset until a controlled remote trial is configured and tested. A successful local video test does not prove remote connectivity or server capacity.

07 / Plain-English terms

The words you will keep seeing.

Open a term whenever the runbook feels unfamiliar.

VPS, SSH, and root

A VPS is your rented Linux computer. SSH is a secure terminal connection to it. Root is its administrator account, which can change the entire machine. The running StageFlow API uses a separate, limited account named stageflow.

DNS, HTTPS, TLS, and WSS

DNS connects a domain name to the server's address. TLS provides the encryption used by HTTPS. WSS is the encrypted form of a WebSocket connection, used for live events. A certificate helps the browser verify that it reached the correct domain.

Nginx, API, and reverse proxy

Nginx accepts public web requests. An API is the program that handles actions such as logging in, joining a room, or requesting a private replay. Nginx acts as a reverse proxy when it forwards a visitor's request to the private API and returns the response.

systemd, service, and timer

systemd is Ubuntu's service supervisor. A service file describes how to run a job, as which user, with which limits. A timer schedules a job. In this profile, the health timer checks readiness and disk space, and the log-rotation timer keeps old nginx logs manageable.

Docker and Compose

A container packages a process and the files it needs. Compose describes several containers together. Here, compose.yml defines dedicated PostgreSQL and Redis containers, their private ports, persistent directories, health checks, and limits. The local fixture Dockerfile is a test environment, not the production app image.

Build, artifact, release, and migration

A build turns source code into runnable files. Those files are build artifacts. A release is a particular version prepared for deployment. A migration changes the database structure to match the new code; the migration job runs explicitly while the API is stopped.

Symlink and rollback

A symlink is a filesystem shortcut. /opt/stageflow/current points at the selected release folder. Rolling back means returning to a compatible earlier version. If the database changed incompatibly, switching the shortcut alone is insufficient: use a tested forward fix or restore the matching database/media backup with compatible code.

WebRTC, FFmpeg, and HLS

WebRTC carries live speaker audio/video between browsers, with TURN helping when needed. When a webinar host records, their browser captures the composed stage and uploads WebM chunks. FFmpeg turns that stream into HLS, a playlist plus small video segments that authorized viewers can play. A meeting does not start this broadcast pipeline.

Allowlist, health check, and monitoring

An allowlist admits only approved client IP addresses. A health check asks whether a dependency or service is ready. Monitoring collects health, errors, traffic, disk use, and resource measurements over time. An alert tells an operator when a measurement needs attention; our current local alert needs to be connected to a notification system.

RPO and RTO

RPO asks “how much recent data could we lose?” RTO asks “how long could recovery take?” The runbook proposes backups at least daily and a 30-minute recovery target after fencing. Those targets still need to be demonstrated using an off-host backup on the actual environment.
