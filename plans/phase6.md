- Use production web output with correct build-time URLs, compiled API/shared/migrations, worker and all 31 Lua assets. No runtime TypeScript or Vite dev server is a production dependency.
- The tested C12 profile is Ubuntu 26.04 LTS on an isolated Linux fixture, with dedicated PostgreSQL/Redis. The user subsequently proposed one shared PostgreSQL instance with separate project databases/logins; discussion is not evidence that the profile was adapted. Shared-service lifecycle, permissions, pool budgets and backup commands require a separate implementation/validation before using that arrangement. StageFlow must never stop another project's database.
- Keep application/resource limits unchanged while collecting evidence. A successful small fixture does not establish a supported audience.

## 5. Execution and evidence rules

1. Use owned `sf_broadcast_<UUID>` databases, unique `sf:itest:*` or smoke namespaces and temporary media roots. Preserve developer services, catalog, namespace owner and unrelated files. Never FLUSHDB or remove a foreign guard to pass a check.
2. Run focused fixture checks before the final affected/release selection. Record commands, versions, source hashes, actual results, errors/retries and cleanup. Keep binary media, credentials and temporary browser artifacts out of Git.
3. The old-data fixture runs the three pre-V3 migrations, inserts representative rows and valid HLS, then applies only the four V3 migrations. Current API retrieval and repeat-run checks must retain the old rows/files. Any later migration-list change must update this asserted boundary deliberately.
4. Run `pnpm check:release` and `pnpm audit:check` against the final implementation. Audit expiry/network failures are failures, not reasons to weaken the gate.
5. Documentation-only updates after successful implementation checks require changed-file formatting, link/anchor validation and `git diff --check`; do not repeat unchanged suites merely to change a status line.
6. Commit the scoped work with the requested C13 message. Keep Actual commit blank inside it, then record its real hash in one follow-up documentation commit.
