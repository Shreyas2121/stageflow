Study page · version 1

StageFlow

StageFlow is a small live stage in the browser. Up to four people on stage see and hear each other directly. In a webinar, everyone else watches a delayed recording of that stage.

This page is for you. It is written the way you would explain the project to a recruiter. The repo only defines version 1. It does not list version 2 or version 3. Anything missing is “not in this version.”

Two kinds of room

You pick the kind of room when you create it. It never changes later.

Meeting

Everyone who gets in is on stage. The fifth person is refused. There is no audience. There is no broadcast.

Webinar

The host is on stage. Everyone else joins as an attendee, with no camera and no direct video link. They can raise a hand. The host can put them on stage, or take them off. The host can also lock someone’s microphone or camera. Attendees watch the broadcast. They do not join the direct call.

Say this A meeting is a call of at most four people. A webinar is that same small stage, plus an audience that only watches.

The demo you can run alone

You do not need three other people to show a four-person call. On the meeting page, click “Spawn demo peer” up to three times.

Each fake person is a real connection. It gets its own guest login, its own socket, a drawn video, and a short beep every four seconds. The drawn video is a canvas: the page paints a picture and sends that picture as if it were a camera. The beep is there so the “who is speaking” highlight moves.

A second browser window is still needed to show a real attendee. The fake people do not replace that. In a webinar, a fake person joins as an attendee. Spawning it does not put it on stage. The host has to promote it, the same as a real person.

Say this I can show a four-person call on one laptop because the extra people are real connections with fake camera and fake sound. A webinar audience still needs a second window.

How the pieces sit

The browser does the camera, the sound, and the direct video links. The API keeps the list of rooms and decides who is allowed on stage. The picture of the call does not travel through the API.

Browser — React

Camera, microphone, screen share, direct links, broadcast player.

Socket.IO — who is here, and the short handshake notes
HTTP — create a room, upload broadcast pieces, play the file

Nest API

Checks the token. Applies the room rules. Does not carry the live video.

Postgres

The saved list: users, rooms, broadcast rows.

Redis

Who is in the room right now.

FFmpeg

Turns the host’s recording into a playable video file.

Video and audio words

These are the words that are new if you have not done video or audio in the browser. Each block is the idea, then where it lives, then a sentence you can say.

The video does not go through Nest

Nest only introduces the browsers. The picture and the sound go from browser to browser. That direct link is called a peer connection. The browser API for it is WebRTC.

Used by the peer manager in the web app.

Say this The server introduces people. The video goes straight from one browser to the other.

Mesh

A mesh means every person on stage has a link to every other person on stage. Two people need one link. Three people need three links. Four people need six links. Each extra person adds a link to everyone already there. That is why the cap is four.

A bigger product would put a media server in the middle. That server is often called an SFU. Each person sends one stream up, and the server sends copies out. Version 1 does not have that.

Say this Four people means six direct links. I capped the stage there on purpose. A media server in the middle is a later design, not this version.

Signaling

Signaling is the Nest socket passing notes: “here is my offer,” “here is my answer,” “here is my network address.” The notes are small text. The video is not inside those notes. Socket.IO is only the messenger.

Event names are shared types in packages/shared. The API gateway relays them. The web client sends them.

Say this Socket.IO carries the handshake. It does not carry the video.

Offer, answer, and glare

Before two browsers can send video, they agree how to talk. One side sends an offer. The other side sends an answer. If both send an offer at the same time, that clash is called glare.

The code picks one side to give in, called polite, and one side to keep its offer, called impolite. The choice is the order of their socket ids. The lower id is polite.

The rule is in packages/shared/src/negotiation.ts. The browser uses it from apps/web/src/features/live/services/peer-manager.ts.

Say this If both browsers start the handshake at once, one side drops its offer and takes the other side’s. The socket id decides which side.

ICE, STUN, and TURN

After the offer and answer, the browsers still have to find a network path. That search is called ICE.

On one laptop the path is just “this computer.” The stats drawer shows that as host. That is normal for the solo demo.

STUN is a small helper that tells a browser its public address, so two people on different networks can try a direct path. TURN is a relay: if a direct path fails, the media can bounce through a server you configure. Version 1 does not require TURN. The demo is meant to work with STUN and the local machine.

Say this On one machine the video never leaves the computer. STUN is for two real networks. A relay server is optional and not required for this version.

Green room

The green room is the screen before you join. You pick a camera, a microphone, and a speaker. You see yourself. You see a live microphone level. If the browser blocks a device, join stays off and the page says which permission failed.

Meeting members and the webinar host must allow the camera and the microphone. Webinar attendees skip this. They have nothing to send. You cannot change devices in the middle of the call in this version.

apps/web/src/features/live/components/green-room.tsx

Say this Devices are chosen before join. Attendees never get that screen, because they are not sending video.

Mute, camera off, screen share, and leave

Mute and camera-off do not hang up. They silence or hide the track that is already sending. In code that is track.enabled. The handshake does not start again.

Screen share swaps the video track in place. The camera stays open in the background so it can come back. In code that swap is replaceTrack. It does not start a new offer.

Leaving the room is different. Leave stops the camera, the microphone, and the screen, and it closes every direct link. That is what turns the camera light off. Turning the camera “off” during the call may leave the light on, because the track is hidden, not stopped.

Say this Mute hides the track. Leave stops it. Screen share swaps the picture without a new handshake.

Broadcast and HLS

People on stage keep the direct links. Attendees do not get those links. They watch a playlist of short video files. That playlist format is called HLS.

The path is:

  1. The host’s browser draws the stage onto a hidden canvas, at 720p.
  2. It mixes the stage sound into one audio stream.
  3. It records that mix and sends about one second of data at a time to Nest.
  4. Nest writes those pieces, in order, into one FFmpeg process.
  5. FFmpeg writes a 720p playlist on the API machine’s disk.
  6. The attendee’s page plays that playlist with hls.js.

The picture the attendee sees is about 8 to 20 seconds behind the live stage. The files are a few seconds long, and the player stays a little behind the newest file. That delay is expected.

When the host stops a healthy broadcast, that same playlist becomes the replay. There is no second copy and no upload to cloud storage.

If FFmpeg cannot start, the broadcast is marked failed. The host sees that FFmpeg is missing. The stage call stays up.

Say this Attendees watch a delayed recording of the stage, not a direct call. The same file is the live broadcast and the replay. If FFmpeg is missing, the call still works.

The stats drawer

While the drawer is open, the page reads each direct link once a second. It shows outbound and inbound bitrate, packet loss, jitter, round-trip time, frame rate, and how the network path was found. Closing the drawer stops the reading. Opening it does not create new links.

Say this The drawer is a live view of each direct link. It is there so you can see the call is real, not a fake tile.

What you already know

The new part is the media. The app around it is Nest, React, and a small amount of Redis.

React

There are three pages: home, the live room, and the replay. The live room keeps its current snapshot in a Zustand store. Room and broadcast fetches use TanStack Query. The socket client and the peer connections live in services, outside the components. Components render tiles. They do not open peer connections themselves.

Say this The React side is pages, a room store, and query hooks. The video engine sits next to React, not inside the components.

Nest

A guest session is a display name plus a JWT. There is no password. The token lasts 12 hours. Rooms are rows in Postgres. A Socket.IO gateway handles join, leave, hands, promote, demote, and the handshake notes. Broadcast pieces are a normal HTTP upload of raw bytes. Controllers stay thin. The rules sit in services.

Say this Nest is the same shape I already use: modules, a socket gateway, and services that own the rules. The new work is what those rules allow.

Redis

Redis is who is in the room right now. Postgres is the fact that the room exists. If Redis is lost, the live room is empty. The saved room row is still there.

Two people joining at the same instant cannot both take the fourth seat. One Lua script checks the cap and writes the seat together. The API does not read a blob, edit it in Node, and write it back. The same pattern covers promote, demote, mute locks, and “a broadcast is already running.”

One API process owns the live keys for an environment. If that process crashes, another process does not take over by itself. A restart clears who is live on purpose, and it keeps the saved rooms. The open page tells you to join again.

Say this Redis is presence, not the database. Lua makes the four-person cap one atomic write, so two joins cannot both win the last seat.

Honest limits

Say these before someone else finds them. They are the edges of version 1, not bugs you forgot.

  • No accounts, email, or passwords. A guest name and a token.
  • No chat, reactions, polls, or scheduling.
  • No fifth person on stage.
  • No media server in the middle.
  • No cloud storage. Broadcast files stay on the API machine.
  • If the host leaves, the room ends. There is no new host.
  • A dropped socket does not resume. You join again.
  • The supported browsers are current Chrome or Edge on Windows.
  • The guest token lasts 12 hours. There is no refresh token.
  • One broadcast at a time, and only in a webinar. One quality: 720p.

If they ask

What is it?

A four-person live stage in the browser, plus a webinar mode where the audience watches a delayed broadcast of that stage. I can demo the four-person call on one laptop.

Why only four people?

Everyone on stage connects directly to everyone else. Four people is six links. Past that, the browser work grows fast. A larger room needs a media server. That server is not in this version.

Why don’t attendees get a direct video link?

An attendee would add a new link to every person on stage. Version 1 keeps the direct links inside the stage. The audience watches one recording of that stage instead.

What is Redis for?

Who is here, who is on stage, who has a hand up, and whether a broadcast is already running. Postgres keeps the room after the call. Redis is the live copy, and the seat cap is one Lua script so two joins cannot both take the last seat.

What if FFmpeg is missing?

The broadcast fails and the page says so. The stage call stays up. People on stage can still see and hear each other.

What does version 1 leave for later?

This repo does not define version 2 or version 3. It does list what this version refuses to be. Not in this version: user accounts, chat, a fifth stage seat, a media server, cloud storage for the recording, more than one video quality, and picking a new host if the host leaves.
