StageFlow is a bounded stage you can demo alone, with the negotiation, the stats, and the broadcast limits made explicit.

StageFlow includes three demo peers, live connection stats, webinar moderation, and one HLS broadcast of the webinar stage. One browser can run a four-person meeting with real peer connections, canvas video, and pulsing generated audio. People on stage can also share a screen, return to the camera, and leave. Meeting participants and webinar hosts choose devices in the green room before joining. A joined stage member can change camera, microphone, and speaker without leaving. A meeting has at most four stage members, counting the host and suspended stage reservations. Webinar attendees join without device prompts, can raise a hand, and have no peer connection or stage video. The host can promote attendees from the ordered hand queue or roster, demote speakers, and lock or unlock their microphones and cameras. Promotion asks for device consent before media starts; demotion stops capture and closes peer connections while keeping the attendee joined. Before the first broadcast, attendees see `The host has not started the broadcast.` A webinar host starts and stops one live broadcast of the current stage. Attendees play it after a short delay, then play the same playlist as a replay. The stage mesh stays usable when FFmpeg cannot start.

Use Node 22.22.1 or newer (`.nvmrc` selects Node 22), pnpm, and Docker Desktop with Linux containers. Postgres 16 uses loopback port 5432, database/user/password `stageflow`, and a named data volume. Redis 7 uses loopback port 6379. Compose publishes both only on `127.0.0.1` and includes health checks. Existing running containers keep their current bindings until recreated; this remediation does not restart developer services.

Keep `.env` out of version control. `pnpm typecheck` checks shared, then the API, then the web app. The API and web `typecheck`, `test`, and `build` commands first verify `@stageflow/shared` and compile it when inputs or output files have changed, including when `packages/shared/dist` is missing. API tests load the root `.env`, execute the real Lua scripts against Redis under unique `sf:itest:*` prefixes, and clean up those keys. Missing or unreachable Redis fails those tests. The first dev process owns the shared watcher; stopping it stops shared compilation. A build or test started while that watcher is running reuses its output instead of starting a second compiler. Shared builds and watchers use one exclusive writer. Compilation buffers output privately and replaces complete files without clearing live declarations. Consumers require the current source/configuration generation and matching emitted files; failed rebuilds cannot reuse an earlier success. Missing output waits for a successful rebuild or reports a bounded timeout; edit the source or restart the watcher to repair it. A dead writer can be reclaimed, while a live writer is preserved. Stop any watcher started with the previous protocol before using the new tooling.

Root `typecheck`, `test`, `test:unit`, `test:integration`, `build`, `check`, and `check:release` commands use `scripts/checks.mjs` to prepare shared once before executing their dependency graph. An unchanged root invocation emits shared once, or reuses a current live watcher. Each app task still verifies its prerequisite, so an edit during a check is rebuilt rather than bypassed. Successful shared build records live under `node_modules/.cache/stageflow-shared-builds`; reuse verifies build sources, inherited TS configs, root/shared manifests, the workspace/lock metadata, TypeScript version, build-helper code, and the complete emitted file set with content hashes. Missing, modified, or extra files trigger a rebuild. `pnpm shared:prepare` and app tasks can reuse a verified prior result across invocations. `pnpm --filter @stageflow/shared build` explicitly recompiles. Shared test sources remain included in `typecheck` and excluded from production emit. Affected package checks prepare shared once before their package tasks.

`pnpm install` installs the Husky pre-commit hook through the root `prepare` script. Unstaged edits are preserved; if they conflict with formatting, the commit fails and lint-staged restores the original changes. Open `http://localhost:5173` in current desktop Chrome or Edge on Windows. Vite loads the root `.env` and requires port 5173. The API uses `http://localhost:4000/api`; Socket.IO attaches to that same HTTP server at `http://localhost:4000`.

The API validates environment configuration with Zod 4 through Nest ConfigModule's native `validationSchema`; its exported typed config uses the same schema. Required values are `JWT_SECRET`, a PostgreSQL `DATABASE_URL`, a Redis/Rediss `REDIS_URL`, and one exact HTTP(S) `CORS_ORIGIN` without a path or trailing slash. `PORT` is an integer from 1 to 65535 and `HOST` defaults to `127.0.0.1`; set a deliberate bind address for a container or remote deployment. Development/test secrets need at least 16 characters. Production rejects known placeholders and requires at least 32 characters; generate at least 32 random bytes and inject the resulting secret through deployment configuration. Do not reuse the example secret. The migration DataSource validates only `DATABASE_URL`, without loading JWT, Redis, CORS, or ICE configuration. API PostgreSQL connection, statement, and client query timeouts are 3, 5, and 6 seconds respectively. These runtime limits are configured separately from the migration DataSource so future DDL is not subject to the API query budget.

To try the meeting on one machine in one browser:

1. Enter a display name, create a **meeting**, enable camera and microphone in the green room, and join.
2. Click **Spawn demo peer** three times. Each demo has its own guest session, socket, canvas camera, and generated microphone. Four tiles appear, and the three demo roster rows have a **Demo** badge. Spawning never requests another device. The button disables while a start is in progress and after three demos. Humans and demos share the same four-person stage cap; a full-stage rejection shows the server message and cleans up the failed demo.
3. Open **Connection stats**. Each remote connection has a row with outbound/inbound bitrate, packet loss, jitter, round-trip time, frame rate, and local ICE type. Stats update once per second; missing values display `—`. The first sample has no rates. ICE type `host` is normal on one machine.
4. Mute your microphone. Each demo emits a short tone every four seconds; a demo's pulse can take the **Speaking** label. If the browser blocks playback, click **Play stage audio and video** in its tile.
5. Click **Remove demo peers**. Their tiles disappear and their tracks, canvas frames, tones, and audio contexts stop. Your camera stays available, and you can spawn again. Leaving, navigating away, room end, or a host disconnect also removes the demos. Leaving stops your camera and microphone too.
6. Create a **webinar**, join as host, and spawn a demo. It stays an attendee with a **Demo** badge, no video tile, and no peer connection. Spawning does not promote it. Click **Promote** on its roster row to put it on stage and open its media connections. **Demote** returns it to an attendee and closes those connections. Demo peers have no screen-share control.

For a meeting with two independent browser windows:

1. As Ava, create a meeting. Click **Enable camera and microphone**, allow both permissions, and check the preview and moving microphone meter. Select the camera, microphone, and speaker before joining. Browsers without speaker selection use their default output. A permission error names the failed device and keeps join disabled.
2. Join the live room. In a second independent window, open the home page, enter Sam and the room slug, enable devices, and join. Each sees the other's camera and hears remote audio; the local tile stays muted. If playback is blocked, click **Play stage audio and video**. Both rosters show Ava as `HOST` and Sam as `SPEAKER`. The host must join a meeting first; a fifth stage member is rejected.
3. As Sam, turn the camera off or mute. Ava's roster flags change and Sam's tile stays mounted. These controls disable captured tracks without renegotiating. Speak to see the **Speaking** border and label; it clears on silence. Click **Share screen** and select a screen or window: the shared tile becomes the large frame. **Stop sharing**, or the browser's own stop control, restores the camera. Screen sharing replaces the video sender track without another offer; the camera stays captured, and an off camera stays off when restored. Cancelling the picker reports an error and leaves the camera in place.
4. Leave as Sam while sharing. Ava's tile and roster entry for Sam disappear. Sam's camera, microphone, and screen tracks stop; peer connections, audio analysis, and video attachments are released. Navigation, room end, and unexpected socket loss also release local media. Unexpected loss reserves the membership for the grace period described below.
5. Create a webinar as Ava. Join as the host. Join that slug as Sam in the other window: Sam needs no device permission, appears as `ATTENDEE`, sees the roster, and has no WebRTC video. Sam can raise or lower a hand visible to Ava. Before the first broadcast, Sam sees **The host has not started the broadcast.** Ava sees the hand queue in raise order and can **Promote** Sam. Sam then enables devices before either window receives their media. Ava can **Lock microphone** or **Lock camera**; Sam cannot enable the matching device until Ava unlocks it, and unlocking leaves it off until Sam uses the existing control. **Demote** stops Sam's capture, closes the connection, and returns Sam to the attendee roster. A meeting has no broadcast controls. A meeting start is rejected with **Broadcast is not available yet.** and creates no broadcast row.
6. Spawn demo peers in the webinar and **Promote** one onto the stage. Click **Start broadcast**. Ava still sees the mesh tiles, not an HLS copy of the stage. Sam gains no device prompt and no peer connection. After the normal delay, Sam's window plays the composite. A wait of about 8–20 seconds is expected.
7. Click **Stop broadcast**. The playlist finishes. Sam plays it with VOD controls in the room. **Open the replay** goes to `/replay/:broadcastId`, and the same guest session plays that page.
8. Ava leaves. The other window shows **This room has ended.** The room remains fetchable with `status: ENDED` and a populated `endedAt`. Leaving also stops a host's canvas recorder, audio mix, and chunk upload, along with the camera and peer connections.
9. Join a new meeting, stop the API, and restart it. Local media stops when the page detects the socket loss. Resume cannot restore presence cleared by API restart: a resume against missing presence shows **The live room reset. Join again.** If the API stays unavailable through the local recovery budget, the page shows **The connection was gone too long. Join again.** The catalog room stays `LIVE`; explicitly prepare devices and join again.

The stage is a full mesh of at most four people, counting the host and speakers together. Attendees stay outside that mesh. The live broadcast is one 720p HLS rendition, and the glass-to-glass delay is about 8–20 seconds. Use current Chrome or Edge on Windows. On one machine, STUN with local loopback normally produces ICE type `host`. TURN is optional and is used only when `TURN_URL`, `TURN_USERNAME`, and `TURN_CREDENTIAL` are set together. `FFMPEG_PATH` defaults to `ffmpeg`. If that binary cannot start, the broadcast becomes `FAILED`, the host sees `FFmpeg is not available. The stage is still up.`, the mesh stays usable, and the attendee sees the error with no player. When an API process becomes the owner of a Redis namespace, it marks every `STARTING`, `LIVE`, or `STOPPING` broadcast `FAILED` with `api restarted` and clears that namespace's live keys. `READY` broadcasts and their playlist files stay, and catalog room rows stay. Each attempt keeps its HLS playlist and segments under `DATA_ROOT` (default `apps/api/data`). That directory grows with every broadcast. A second start while one broadcast is active returns `A broadcast is already active.`

A joined stage member can change camera, microphone, and speaker without leaving. Mute and a host lock apply to the replacement. A camera chosen during screen share is restored when the share stops. A lost camera or microphone mutes that input and waits for a deliberate choice. Speaker selection uses `setSinkId` where the browser provides it, including a later stage tile, the attendee broadcast, and the replay. The saved value is that output id for this tab. An unsupported browser keeps the default speaker. Attendees do not grant capture permission unless promoted. The first stage join still requires both a camera and a microphone.

An unexpected human signaling-socket drop reserves the same membership for **20 seconds after the server detects the loss**. The participant id, role, host locks, join order, and raised hand stay. A suspended stage member still counts toward four; a host can demote a suspended speaker to free that slot. The page shows **Reconnecting. This room is still open.** as soon as it detects loss, and stops its camera, microphone, screen share, peers, analysers, demos, and upload producer. It opens fresh sockets at 0, 1, 2, and 4 seconds from local detection and starts no attempt at or after 20 seconds. Server and page detection can occur at different times. Old SDP, ICE, media, and moderation commands are discarded. An ICE/media failure while the signaling socket stays connected does not trigger this recovery.

Resume is limited to the same live page and a valid guest JWT. Its credential stays in page memory, outside `sessionStorage` and `localStorage`. Success restores the membership from a fresh snapshot and creates new peers only between connected stage members. Microphone and camera stay off until an explicit device action; host locks still block the matching device. Screen sharing stays off, demos stay stopped until **Spawn demo peer**, and a broadcast does not restart automatically. Attendees resume with no capture request and no WebRTC peer connection.

Explicit **Leave room**, page hide, navigation, and component disposal cancel recovery and discard the credential. A lost or unsent leave during tab close can hold the slot until grace expiry. Refresh, browser restart, guest-token expiry, API restart, Redis presence reset, and another device do not resume the old membership. A fresh page with the same guest but no credential receives **This guest is already in the room.** while the reservation remains. Expiry frees a guest's slot. A delivered host leave or host grace expiry ends the catalog room.

Unexpected host loss fails the current broadcast with `Host connection lost.`, rejects later chunks with `broadcast_not_active`, and keeps the catalog room `LIVE` until host grace expiry or a delivered host leave. After resume, the host can use **Start broadcast** to create a new attempt. A suspended non-host is removed from the compositor inputs while the current broadcast continues. Explicit host leave still uses the graceful stop path; a clean stop can become `READY`. API restart still clears presence and fails in-flight broadcasts with `api restarted`.

Room chat is one plain-text channel for connected hosts, speakers, and attendees in both meetings and webinars. The panel appears after join and shows each accepted message once, in server order, with the sender's name and role at acceptance. Enter sends; Shift+Enter inserts a newline. Text and URLs stay literal text. An arrival preserves focus and, when you are reading earlier lines, shows a new-message count instead of scrolling to the bottom. Demo peers generate no chat lines.

| Chat limit                | Shipped behavior                                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Text                      | 1 to 1,000 UTF-16 code units after trim and at most 4,000 UTF-8 bytes; some emoji use two code units                    |
| Retained history          | At most 500 recent messages per room in Redis; the oldest messages are dropped                                          |
| Idle expiry               | 86,400 seconds (24 hours), refreshed by chat writes                                                                     |
| History pages             | Latest 50 messages by default, in ascending sequence; requests allow 1 to 100 per page                                  |
| Participant rate          | 10 accepted messages per participant per 10 seconds                                                                     |
| Room rate                 | 100 accepted messages per room per 10 seconds                                                                           |
| Pending sends             | At most 5 waiting for an acknowledgement; a sixth stays in the composer with a busy message                             |
| Retry deduplication       | Latest 500 participant/request-id pairs per room; an accepted duplicate spends no rate and returns the original message |
| Participant-rate capacity | At most 1,000 fields per room; a new field past the cap returns `chat_busy` without evicting an existing field          |
| Chat work queue           | At most 32 waiting operations per room, separate from stage work; excess returns `chat_busy`                            |

**Pause chat** blocks every new message, including the host's and a synthetic participant's. Everyone sees **The host paused chat.** Accepted lines remain readable. **Resume chat** permits new sends again. Join and socket resume fetch recent history. During recovery the panel is read only; in-flight sends become **Not sent**, and the page does not send them again automatically. **Retry** uses the original request id; **Dismiss** removes the failure without sending it. A retry after its dedup entry has fallen outside the latest 500 pairs can create another message. A gap lost to retention shows **Earlier messages are no longer available.** Chat events also use the existing socket event budget. A rejected, busy, or rate-limited send stays on chat and leaves the stage, peer connections, and broadcast running.

The panel states **Chat is live. It is not synced to the delayed video.** Room end disables both the composer and Retry, keeps the lines already on the current page, and shows **This room has ended. Chat is closed.** Shutdown deletes the room's chat keys, and API startup clears chat with live presence. Chat is temporary Redis state: no messages are stored in the PostgreSQL catalog or attached to a replay. The server stores `sentAt`, but the panel does not yet display it; the master plan's visible-timestamp requirement remains missing implementation.

Producer health (RC06): native recorder errors, unexpected stops, and 12 seconds without a nonempty blob stop the local producer and request server stop while preserving room media. FFmpeg allows 20 seconds for first input and subsequent inactivity; only completed nonempty writes renew that deadline. Producer loss follows the existing FAILED cleanup path. Normal stop retains the 10-second child exit bound. Broadcast stop acknowledgements allow 15 seconds and reconcile READY/FAILED snapshots for the same attempt if the acknowledgement is lost. An unresolved stop reports that confirmation is pending. Producers do not restart automatically.

Page lifecycle (RC07): pagehide releases camera, microphone, screen capture, peers, demo peers, speaker analysis, and recorder/upload resources immediately, including when the browser retains the document in its back/forward cache. It closes signaling without waiting for leave, stop, or upload acknowledgements. A delivered host leave ends the room immediately. If page exit reaches the server only as socket loss, the host reservation and catalog room can remain until grace expiry, and the interrupted broadcast fails. RC06 producer-loss protection bounds an abandoned encoder if disconnect delivery is delayed. On pageshow after exit, the page stays in the lobby and asks the user to join again. Stage members must enable devices again; attendees can join without capture. Nothing restarts automatically, and a host room that the server has ended stays ended. Switching tabs alone does not trigger this exit policy.

Guest sessions stay in `sessionStorage` under `stageflow.session`. A new independent tab starts without a session; a direct room URL asks for a name on the home page. While a usable session is present, home create and join reuse that session and do not create another guest. **Use a different name** clears the current session, and the next submit starts a different guest. The same display name does not recover the earlier rooms. A fresh replay visitor can enter a name directly on the replay page and stays on that replay; that guest is a new user and does not inherit the host's room list. Room data is fetched with TanStack Query, keyed by slug and token. Display names and titles render as text.

The home list shows rooms created by the current guest session. `LIVE` in that list is the catalog status: the room has not ended, and it does not mean someone is connected. Join accepts a raw slug or a room link from this app. The copied invitation is the page origin plus `/r/` plus the slug. A recording shows `STARTING`, `LIVE`, `STOPPING`, `READY`, or `FAILED`. Only a `READY` row with a catalog playlist opens the replay. `thumbnailUrl` is optional, and this build does not generate thumbnails.

The HTTP routes are `POST /api/sessions/guest`, `POST /api/rooms`, `GET /api/rooms`, `GET /api/rooms/:slug`, `GET /api/rooms/:slug/broadcasts`, `GET /api/broadcasts/:id`, `GET /api/broadcasts/:id/thumbnail.jpg`, `POST /api/broadcasts/:id/chunks`, `GET /api/broadcasts/:id/hls/:file`, `GET /api/health`, and `GET /api/health/live`. `GET /api/rooms` lists rooms for the current guest as `{ items, nextCursor }`. A caller-supplied host id does not change that list. `GET /api/rooms/:slug/broadcasts` returns `{ items, nextCursor }`, default 20 and maximum 50, ordered by newest creation time, then id. `GET /api/rooms/:slug` and `GET /api/broadcasts/:id` stay in this list. Room, broadcast catalog, playlist, and segment calls require a guest bearer token. Catalog JSON exposes `playlistUrl` as `/api/broadcasts/:id/hls/index.m3u8` or null. `thumbnailUrl` is `/api/broadcasts/:id/thumbnail.jpg` or null, and this build does not generate thumbnails. Filesystem paths stay off the JSON. Playback attaches that bearer token only to the same-origin playlist and its `segment######.ts` files. An absolute or cross-origin media URL is rejected and does not receive the token. HTTP and Socket.IO share HS256 verification, UUID subject checks, and a real user lookup. Tokens expire after 12 hours. `GET /api/health` checks PostgreSQL only and returns `{ "ok": true }` or HTTP 503 `{ "ok": false }`. It stays successful when Redis is down, so a database probe must not restart the process. `GET /api/health/live` uses the same response shape for the live Redis session.

Live presence is server-owned Redis state. Lua enforces stage limits, roles, media flags, and hands atomically; snapshots carry increasing revisions. Before clearing any presence, startup pings Redis and acquires a unique non-expiring `<LIVE_NAMESPACE>:owner` guard with `SET NX`. An existing guard prevents listening and prevents cleanup. Startup then clears only `<LIVE_NAMESPACE>:room:*`; catalog rows and independent test/environment keys remain intact. A delivered host leave or host grace expiry ends the catalog room and removes its live keys. Unexpected human socket loss suspends the membership; a synthetic socket loss leaves immediately. Host suspension removes all remaining synthetic memberships. On graceful application shutdown, readiness drops, pending live operations drain, the server closes, and the owner guard is released with a compare-token delete. Unexpected Redis loss still disconnects sockets and exits within one second without ending catalog rooms or reconnecting to Redis. A PostgreSQL error does not exit the process. Socket resume cannot survive the startup presence reset.

Local `pnpm dev` does not force-kill the API as its first step. The supervisor compiles with `nest build --watch` and runs the API separately. Nest's own `start --watch` path on Windows uses `taskkill /T /F`, which skips shutdown and leaves the owner guard behind, so a shared-package rebuild and a successful API compile both ask the running API to close through a private channel instead. That channel is a named pipe on Windows, or a socket under the temp directory on other systems. It is not an HTTP route and it is not bound to a public address. The API opens it before acquiring the owner guard. The supervisor waits up to 15 seconds for that process and its child processes to exit, which lets Nest close FFmpeg's input and release only this process's guard. If the close misses the deadline, the supervisor force-stops the tree and prints that the guard may still be held. It does not delete the guard, and it does not start a replacement owner. Use the manual recovery steps below after that forced stop, a crash, or Redis loss. A routine graceful dev restart does not need them.

Live Redis supports **standalone Redis only**, with one active API owner per namespace. `LIVE_NAMESPACE` accepts 1 to 64 letters, digits, underscores, or hyphens and defaults to `sf_<NODE_ENV>` (`sf_development`, `sf_test`, or `sf_production`); the example explicitly uses `sf_development`. Existing explicit namespaces remain honored. Use separate Redis namespaces and PostgreSQL databases for independent environments: namespacing live state does not isolate catalog rows. The owner guard has no expiry or automatic takeover. After a crash, forced stop, Redis connection loss, or partial startup failure, a surviving guard fails closed. Stop the previous API and its supervisor, confirm that no process can still act for that namespace, inspect that exact owner key, then use an administrative Redis client to remove only `<LIVE_NAMESPACE>:owner` and restart one API. Never remove the guard of a running owner or clear a whole Redis database to recover. If Redis lost the guard during restart, startup can acquire it normally. Configure supervisors to back off on startup failure and alert on a retained guard; this is a deliberate manual recovery policy, not multi-instance failover.

Live scripts receive nine actual Redis room keys through `KEYS`, in order: revision, participants, stage, hands, ending intent, active broadcast, transports, resume verifiers, and deadlines. `KEYS[6]` remains the active-broadcast lock. The participants hash, stage set, and hand queue use participant ids; the transports hash maps a socket id to its participant id. The resume hash stores SHA-256 verifiers, and the deadline sorted set stores grace deadlines. Raw resume credentials never enter a participant or snapshot. A changed command updates affected entries and refreshes the existing live-key TTLs, returning one atomic revisioned snapshot. No-ops and rejections without overdue expiry retain their revision and TTL policy. Join and resume process overdue expiry first, so expiry may advance the revision even if that join or resume is rejected. A repeated host-ending leave still refreshes the ending intent. Full-roster snapshot reads remain. Scripts normally run with `EVALSHA`; a `NOSCRIPT` miss falls back to `EVAL` to populate Redis's script cache. Other failures are not automatically replayed.

The migrations create `users`, `rooms`, and `broadcasts`, and add `rooms_host_created_idx` on `rooms` (`host_id`, `created_at DESC`, `id DESC`) for the current guest's room list. Schema synchronization and startup migrations are disabled. Phases 3 through 5 add no migration. The broadcasts migration adds the webinar broadcast table. Promote, demote, hand, and host-lock commands use the existing stage scripts. Registered accounts remain outside this build. Existing replay links remain usable by any guest who has the link.

For deployment, terminate TLS at the ingress, use the exact HTTPS frontend origin, and restrict direct API access to the ingress when trusting its forwarding headers. `TRUSTED_PROXIES` is an explicit comma-separated list of proxy IPs, blank by default. Only a trusted immediate peer enables right-to-left `X-Forwarded-For` processing, stopping at the first untrusted hop. Malformed/oversized chains fall back to the immediate peer. Do not use a trust-all proxy setting; the ingress must append or overwrite forwarded addresses correctly. HTTP and sockets share this identity policy. Socket handshakes also enforce the configured origin for WebSocket transport; native clients without an Origin still require a valid guest JWT.

Network and socket admission is process-local and configurable. Those rate counters have fixed windows (`RATE_WINDOW_MS=60000`) and at most `RATE_KEYS_MAX=10000` identities each. A full counter map rejects new identities until entries expire; it never evicts active counters to admit another identity. HTTP admission runs before JSON parsing and the guest controller, returns 429 with `rate_limited` and `Retry-After` set to the remaining whole seconds of the window that rejected the request, and leaves GET health probes available. HLS reads and chunk uploads use separate counters, so playback on a shared address cannot spend the host upload allowance. CORS runs before admission so allowed browser clients can read those errors. Guest creation also has a separate in-flight ceiling that stays occupied until its write/sign operation settles, even after the request disconnects. Socket authentication is bounded before user lookup, and command rates are counted by verified user ID across sockets, including invalid payloads. Rejected commands receive `rate_limited` or `server_busy` before queueing; `room:leave` bypasses command rates. Chat adds the separate Redis rate and capacity limits stated above, and its events still spend the socket event budget.

Cleanup takes priority over waiting normal work at each queue boundary and has separate bounded capacity in both scopes. Repeated leave work for one socket coalesces into the active attempt and at most one retry after a failure. Suspension and expiry use the same cleanup reserve; the sweeper retries failed suspensions while retaining the original grace deadline. In-flight operations finish in order; cleanup does not interrupt an active database/Redis mutation. Exhausting the cleanup reserve is an explicit busy failure, not an unbounded queue or a promise of instant cleanup during dependency stalls. PostgreSQL and Redis I/O timeouts limit ordinary stalls. These are admission budgets, not attendee caps or token expiry rules: the stage still holds four participants and guest JWTs still expire after 12 hours. Broadcast chunk uploads are `application/octet-stream`, capped at 2,000,000 bytes by their own parser. That parser does not raise `HTTP_BODY_BYTES`. `HLS_RATE_LIMIT` counts playlist and segment reads. `UPLOAD_NETWORK_RATE_LIMIT` counts chunk posts before the parser. `UPLOAD_USER_RATE_LIMIT` and `UPLOAD_ATTEMPT_RATE_LIMIT` count them again after the authenticated host check. Those counters are separate from ordinary `HTTP_RATE_LIMIT` requests. They are admission budgets, not an attendee cap. Before public guest issuance, set them for expected shared-network traffic, monitor rejections and guest-row growth, and establish retention and abuse response for persistent guest data.

Connection stats sample immediately when the drawer opens and then once per second. Closing the drawer stops polling and clears the baseline; reopening starts rates/loss with a fresh sample. Each peer read has an 800 ms deadline and only one native read may remain outstanding per connection, including across reopen. A stalled/rejected read shows unavailable metrics while healthy peers continue, and late expired reports are ignored. Missing or non-advancing report timestamps also reset that peer. Opening, closing, or recovering stats creates no peer connections.

Off-stage media state is canonical: microphone muted, video off, screen sharing off. Webinar attendees, including demos, join with these flags regardless of their requested device flags. Off-stage activation patches return `not_on_stage` without changing state/revision/TTLs; empty or already-off patches are no-ops. A safe patch repairs legacy noncanonical flags as one changed revision. Demotion normalizes the same fields, while promotion keeps them off until an allowed stage update. Hands, locks, identity, and Demo badges retain their meaning; media flags do not grant stage membership or prove actual capture/transmission. Public promote, demote, and host-lock handlers enforce the server-owned stage rules. A meeting start returns `broadcast_not_available` (`Broadcast is not available yet.`) and writes no broadcast row. A webinar host can start one broadcast at a time. The room snapshot's `broadcast` field is the in-flight attempt, or the newest attempt when none is in flight, and it is null before the first attempt.

RC16 upload work budgets: the browser holds at most 8 unsent blobs and 8,000,000 bytes, counting the active request, and aborts a chunk request after 10 seconds. Exceeding either queue budget or failing a request ends the producer through the existing broadcast failure path. Normal finish retains its shorter 8-second drain bound. The API appends chunk hashes only after successful FFmpeg writes without copying prior history. Hash storage remains proportional to recording chunks; encoder concurrency, recording retention, and catalog pagination remain separate deployment decisions.
