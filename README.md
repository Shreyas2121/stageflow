# StageFlow

StageFlow supports guest entry, email/password host accounts, optional Google sign-in, scheduled meetings and webinars with waiting admission, owner-managed replay visibility and deletion, and moderated questions with a featured question on the webinar video. The [V3 master plan](MASTER_PLAN_V3.md) defines the product scope. Replay privacy and deletion follow [plans/phase3.md](plans/phase3.md), with implementation and verification in [plans/phase3/guide.md](plans/phase3/guide.md). Scheduled rooms and admission follow [plans/phase4.md](plans/phase4.md), with implementation and verification in [plans/phase4/guide.md](plans/phase4/guide.md). Moderated questions follow [plans/phase5.md](plans/phase5.md), with implementation and verification in [plans/phase5/guide.md](plans/phase5/guide.md). The identity contract is [plans/phase1.md](plans/phase1.md), and its implementation sequence and verification records are in [plans/phase1/guide.md](plans/phase1/guide.md).

The [V2 master plan](MASTER_PLAN_V2.md) records the workspace, device, reconnect, and chat contracts that continue to apply. The workspace contract is [plans/V2/phase1.md](plans/V2/phase1.md), and its implementation sequence is [plans/V2/phase1/guide.md](plans/V2/phase1/guide.md). A joined stage member can change camera, microphone, and speaker without leaving. The device contract is [plans/V2/phase2.md](plans/V2/phase2.md), and its implementation sequence is [plans/V2/phase2/guide.md](plans/V2/phase2/guide.md). An eligible live member can resume the same membership within a 20-second socket-loss grace period. The reconnect contract is [plans/V2/phase3.md](plans/V2/phase3.md), and its implementation and verification records are in [plans/V2/phase3/guide.md](plans/V2/phase3/guide.md). Connected hosts, speakers, attendees, and waiters share bounded room chat with recent history and host pause. The chat contract is [plans/V2/phase4.md](plans/V2/phase4.md), and its slice hashes and verification records are in [plans/V2/phase4/guide.md](plans/V2/phase4/guide.md). Combined acceptance is recorded in [plans/V2/phase5.md](plans/V2/phase5.md) and [plans/V2/phase5/guide.md](plans/V2/phase5/guide.md): UX-01 and QA-01 are verified, QA-02 is partial, and QA-03 is this record. V1 phase records are in [plans/V1](plans/V1/README.md). The capabilities below include host accounts, the guest workspace, the V1 stage, in-call device changes, bounded reconnect, and room chat, with the remaining verification gaps stated below.

StageFlow is a bounded stage you can demo alone, with the negotiation, the stats, and the broadcast limits made explicit.

StageFlow includes three demo peers, live connection stats, webinar moderation, and one HLS broadcast of the webinar stage. One browser can run a four-person meeting with real peer connections, canvas video, and pulsing generated audio. People on stage can also share a screen, return to the camera, and leave. An immediate stage join uses the green room; scheduled members and live meeting joiners held for admission wait without media until a stage seat is granted. A joined stage member can change camera, microphone, and speaker without leaving. A meeting has at most four stage members, counting the host and suspended stage reservations. Webinar attendees join without device prompts, can raise a hand, and have no peer connection or stage video. The host can promote attendees from the ordered hand queue or roster, demote speakers, and lock or unlock their microphones and cameras. Promotion asks for device consent before media starts; demotion stops capture and closes peer connections while keeping the attendee joined. Before the first broadcast, attendees see `The host has not started the broadcast.` A webinar host starts and stops one live broadcast of the current stage. Attendees play it after a short delay, then play the same playlist as a replay. The stage mesh stays usable when FFmpeg cannot start.

On the home page, enter a display name and create or join a room to start a guest session. Guest tokens last **12 hours**, and the list says **Rooms from this guest session**. Create and join reuse that session. **Use a different name** clears it so the next create or join starts a new guest. The same display name cannot recover rooms from an earlier guest session. Demo peers keep their own guest sessions.

While signed out, **Register** uses the display-name field above, an email, and a password. **Log in instead** opens the login form for an existing account. Email is trimmed and lowercased. A host token lasts **7 days**; signing in with the same email on another browser returns to **Your rooms**. Host create and join reuse that token. No extra service or Google credentials are required for these accounts.

As a guest, **Create host account** promotes only the user named by the current guest token. It keeps that user id, display name, rooms, and broadcasts, then replaces the guest token with a host token; the previous guest token fails. Leave every live room membership, including a suspended one, before promoting. A taken email leaves the guest unchanged. Register always creates a separate user. Logging in from a guest session replaces the browser session; rooms that were not promoted stay on that guest and are not merged into the account.

**Log out** clears the browser's stored session for this tab; it does not revoke tokens on other clients. **Change password** requires the current password, stores the replacement, invalidates older tokens for that user, and returns a new host token. Older tokens fail API requests and subsequent socket handshakes/resume; existing connected sockets are not actively evicted. There are no refresh tokens. Email verification and password-reset mail are not in this build, and a forgotten password has no automated recovery.

Google sign-in appears only when all three Google API settings are configured together; leaving them empty is the local default. While unset, home shows no Google control, the availability probe returns `{ enabled: false }`, and start, callback, ticket, and link refuse with `google_unavailable`. Register, email/password login, guest promotion, guest entry, and demo peers do not call Google. The optional Google contract is [plans/phase2.md](plans/phase2.md), with implementation and verification in [plans/phase2/guide.md](plans/phase2/guide.md).

**Continue with Google** signs in by the verified Google subject. An unknown subject creates a separate host with no email or password. A matching Google email does not take over an existing account, merge users, or move its rooms. Google sign-in does not promote the current guest; it starts a separate host. A signed-in host uses **Link Google** with the current host token to link an unused subject. A subject owned by another user is refused without changing either account. A Google-only host has no password: password change returns `password_not_set`, and this build has no set-password flow.

Google transactions require an HttpOnly browser cookie. HTTPS uses a Secure, host-only cookie; HTTP callbacks are allowed only on loopback for development. Frontend and API must use the same site and scheme so the SameSite=Lax cookie accompanies credentialed API requests; different ports on the same loopback hostname work locally. A cross-site frontend/API layout fails closed and is unsupported by this flow. One browser has one active Google attempt; starting another replaces its proof, so an older attempt must be restarted. The callback returns a single-use ticket in the URL fragment, and the return page removes it before redemption. Linking requires the exact initiating bearer, checked before and after provider exchange; logout, switching accounts, expiry, or password change prevents completion. Keep Google unconfigured for public use until a real provider round trip has been recorded; current browser verification uses a controlled exchange. Do not log callback queries, codes, or ticket request bodies at ingress.

Use Node 22.22.1 or newer (`.nvmrc` selects Node 22), pnpm from `package.json`, and Docker Desktop with Linux containers. Postgres 16 uses loopback port 5432, database/user/password `stageflow`, and a named data volume. Redis 7 uses loopback port 6379. Compose publishes both only on `127.0.0.1` and includes health checks. Existing running containers keep their current bindings until recreated; this remediation does not restart developer services.

Copy the example only on first setup; keep any existing `.env` values. Keep `.env` out of version control. `pnpm typecheck` checks shared, then the API, then the web app. The API and web `typecheck`, `test`, and `build` commands first verify `@stageflow/shared` and compile it when inputs or output files have changed, including when `packages/shared/dist` is missing. Their `dev` commands use the shared watcher. `pnpm dev` watches that package and runs both apps. `pnpm build` builds both apps. `pnpm test` runs shared tests, web tests, then the API suite. `pnpm test:unit` is shared and web. `pnpm test:integration` is the API suite. `pnpm check` runs typecheck, lint, test, both builds, and the format check. API tests load the root `.env`, execute the real Lua scripts against Redis under unique `sf:itest:*` prefixes, and clean up those keys. Missing or unreachable Redis fails those tests. The first dev process owns the shared watcher; stopping it stops shared compilation. A build or test started while that watcher is running reuses its output instead of starting a second compiler. Shared builds and watchers use one exclusive writer. Compilation buffers output privately and replaces complete files without clearing live declarations. Consumers require the current source/configuration generation and matching emitted files; failed rebuilds cannot reuse an earlier success. Missing output waits for a successful rebuild or reports a bounded timeout; edit the source or restart the watcher to repair it. A dead writer can be reclaimed, while a live writer is preserved. Stop any watcher started with the previous protocol before using the new tooling.

Root `typecheck`, `test`, `test:unit`, `test:integration`, `build`, `check`, and `check:release` commands use `scripts/checks.mjs` to prepare shared once before executing their dependency graph. An unchanged root invocation emits shared once, or reuses a current live watcher. Each app task still verifies its prerequisite, so an edit during a check is rebuilt rather than bypassed. Successful shared build records live under `node_modules/.cache/stageflow-shared-builds`; reuse verifies build sources, inherited TS configs, root/shared manifests, the workspace/lock metadata, TypeScript version, build-helper code, and the complete emitted file set with content hashes. Missing, modified, or extra files trigger a rebuild. `pnpm shared:prepare` and app tasks can reuse a verified prior result across invocations. `pnpm --filter @stageflow/shared build` explicitly recompiles. Shared test sources remain included in `typecheck` and excluded from production emit. Affected package checks prepare shared once before their package tasks.

`pnpm install` installs the Husky pre-commit hook through the root `prepare` script. Each commit runs lint-staged to format staged files with Prettier and restage the results; formatting failures block the commit. Unstaged edits are preserved; if they conflict with formatting, the commit fails and lint-staged restores the original changes. Run `pnpm format` to format the repository or `pnpm format:check` to check it without writing changes. Generated output, the lockfile, local API data, and environment files are excluded. Files use LF line endings on every platform.

`pnpm lint` covers package source, tests, Vite/Vitest configs, the root ESLint config, and tooling scripts. Web lint enforces Hooks ordering and dependencies. Production TypeScript source also checks floating and misused promises with type information; tests and tool configs retain the basic rules. Import rules keep each app separate and shared source independent of app, browser-framework, and Node packages.

Each lint command keeps a content cache under its working directory's `node_modules/.cache/eslint`. Because that cache cannot see imported types, the command also fingerprints the package closure that can change type-aware results. API includes API, shared source, and shared declarations. Web includes web, shared source, and shared declarations. Shared includes its own source. Those closures also include the root ESLint config, base TypeScript config, root manifest, workspace file, lockfile, and `scripts/lint.mjs`. The root config command fingerprints that ESLint and lockfile metadata plus tooling scripts, and it does not read application source. Each invocation reads a file once. A web-only edit leaves the API and shared caches reusable. A shared source or declaration change invalidates API and web. An ESLint config or lockfile change invalidates every lint cache, and a base TypeScript config change invalidates API, web, and shared. `tsconfig.check.json` in each package writes a separate `node_modules/.cache/typescript/check.tsbuildinfo`; production builds keep their existing configs and emit behavior. To measure a cold check, remove only these cache directories. They contain no credentials and are ignored with `node_modules`.

Open `http://localhost:5173` in current desktop Chrome or Edge on Windows. Vite loads the root `.env` and requires port 5173. The API uses `http://localhost:4000/api`; Socket.IO attaches to that same HTTP server at `http://localhost:4000`.

The API validates environment configuration with Zod 4 through Nest ConfigModule's native `validationSchema`; its exported typed config uses the same schema. Required values are `JWT_SECRET`, a PostgreSQL `DATABASE_URL`, a Redis/Rediss `REDIS_URL`, and one exact HTTP(S) `CORS_ORIGIN` without a path or trailing slash. `PORT` is an integer from 1 to 65535 and `HOST` defaults to `127.0.0.1`; set a deliberate bind address for a container or remote deployment. Development/test secrets need at least 16 characters. Production rejects known placeholders and requires at least 32 characters; generate at least 32 random bytes and inject the resulting secret through deployment configuration. Do not reuse the example secret. The migration DataSource validates only `DATABASE_URL`, without loading JWT, Redis, CORS, or ICE configuration. API PostgreSQL connection, statement, and client query timeouts are 3, 5, and 6 seconds respectively. These runtime limits are configured separately from the migration DataSource so future DDL is not subject to the API query budget.

Registered hosts can choose **Schedule meeting** or **Schedule webinar**, enter a UTC instant such as `2026-11-06T15:00:00.000Z`, and share the existing room invitation. The library shows `SCHEDULED` and that UTC instant. A past or future advertised time never starts the room: the host must choose **Start** inside it. Guest create remains immediate `LIVE`; a registered host can still use **Create meeting** or **Create webinar** for an immediate room.

Open a scheduled slug and choose **Join waiting room**. Early joiners wait off stage without camera/microphone capture or a peer connection, even before the host arrives. The host sees the waiting names and participant ids in arrival order. Waiting is capped at 100; another join is rejected without taking a stage seat. A dropped waiter has no reconnect grace or resume credential; before Start, rejoining creates a new membership at the back of the queue. A pre-start host who leaves or disconnects is removed without grace or a resume credential, and the room stays scheduled. Once the server places someone on stage, the green room asks for explicit device consent before capture begins.

**Start** seats the host first. In a meeting with **Require host admission** off, the oldest waiters fill the remaining seats up to four, counting suspended reservations. A freed seat pulls the oldest waiter, and a newcomer cannot take a free seat ahead of that queue. With admission on, Start seats only the host; **Admit** moves one chosen waiter into a free seat. A full stage leaves that person waiting, and a departure does not admit the next waiter automatically. Scheduled webinar Start instead releases all waiters as attendees, with no stage seat or peer connection; broadcasting still requires the separate **Start broadcast** action. **Spawn demo peer** is available only while the host is live and on stage, and demo peers never wait.

The host can **Remove** one waiter without seating anyone else. Before Start, **Cancel room** reveals **Cancel this room** and **Keep waiting**. Confirmation ends the scheduled room, clears its waiting memberships, and creates no broadcast. A live room cannot be cancelled through this control. The [phase contract](plans/phase4.md#5-system-contracts) and [execution guide](plans/phase4/guide.md) record the schedule, admission, and verification limits.

To try the meeting on one machine in one browser:

1. Enter a display name, create a **meeting**, enable camera and microphone in the green room, and join.
2. Click **Spawn demo peer** three times. Each demo has its own guest session, socket, canvas camera, and generated microphone. Four tiles appear, and the three demo roster rows have a **Demo** badge. Spawning never requests another device. The button disables while a start is in progress and after three demos. Humans and demos share the same four-person stage cap; a full-stage rejection shows the server message and cleans up the failed demo.
3. Open **Connection stats**. Each remote connection has a row with outbound/inbound bitrate, packet loss, jitter, round-trip time, frame rate, and local ICE type. Stats update once per second; missing values display `—`. The first sample has no rates. ICE type `host` is normal on one machine.
4. Mute your microphone. Each demo emits a short tone every four seconds; a demo's pulse can take the **Speaking** label. If the browser blocks playback, click **Play stage audio and video** in its tile.
5. Click **Remove demo peers**. Their tiles disappear and their tracks, canvas frames, tones, and audio contexts stop. Your camera stays available, and you can spawn again. Leaving, navigating away, room end, or a host disconnect also removes the demos. Leaving stops your camera and microphone too.
6. Create a **webinar**, join as host, and spawn a demo. It stays an attendee with a **Demo** badge, no video tile, and no peer connection. Spawning does not promote it. Click **Promote** on its roster row to put it on stage and open its media connections. **Demote** returns it to an attendee and closes those connections. Demo peers have no screen-share control.

For a meeting with two independent browser windows:

1. As Ava, create a meeting. Click **Enable camera and microphone**, allow both permissions, and check the preview and moving microphone meter. Select the camera, microphone, and speaker before joining. Browsers without speaker selection use their default output. A permission error names the failed device and keeps join disabled.
2. Join the live room. In a second independent window, open the home page, enter Sam and the room slug, enable devices, and join. Each sees the other's camera and hears remote audio; the local tile stays muted. If playback is blocked, click **Play stage audio and video**. Both rosters show Ava as `HOST` and Sam as `SPEAKER`. The host must join a meeting first; a fifth stage member is rejected.
3. As Sam, turn the camera off or mute. Ava's roster flags change and Sam's tile stays mounted. These controls disable captured tracks without renegotiating. Speak to see the **Speaking** border and label; it clears on silence. Click **Share screen** and select a screen or window: the shared tile becomes the large frame. **Stop sharing**, or the browser's own stop control, restores the camera. Screen sharing replaces the video sender track without another offer; the camera stays captured, and an off camera stays off when restored. Cancelling the picker reports an error and leaves the camera in place.
4. Leave as Sam while sharing. Ava's tile and roster entry for Sam disappear. Sam's camera, microphone, and screen tracks stop; peer connections, audio analysis, and video attachments are released. Navigation, room end, and unexpected socket loss also release local media. Unexpected loss reserves the membership for the grace period described below.
5. Create a webinar as Ava. Join as the host. Join that slug as Sam in the other window: Sam needs no device permission, appears as `ATTENDEE`, sees the roster, and has no WebRTC video. Sam can raise or lower a hand visible to Ava. Before the first broadcast, Sam sees **The host has not started the broadcast.** Ava sees the hand queue in raise order and can **Promote** Sam. Sam then enables devices before either window receives their media. Ava can **Lock microphone** or **Lock camera**; Sam cannot enable the matching device until Ava unlocks it, and unlocking leaves it off until Sam uses the existing control. **Demote** stops Sam's capture, closes the connection, and returns Sam to the attendee roster. A meeting has no broadcast controls. A meeting start is rejected with **Broadcast is not available yet.** and creates no broadcast row.
6. Spawn demo peers in the webinar and **Promote** one onto the stage. Click **Start broadcast**. Ava still sees the mesh tiles, not an HLS copy of the stage. Sam gains no device prompt and no peer connection. After the normal delay, Sam's window plays the composite. A wait of about 8–20 seconds is expected.
7. Click **Stop broadcast**. The playlist finishes. Sam plays it with VOD controls in the room. **Open the replay** goes to `/replay/:broadcastId`, and the same guest session plays that page.
8. Ava leaves. The other window shows **This room has ended.** The room remains fetchable with `status: ENDED` and a populated `endedAt`. Leaving also stops a host's canvas recorder, audio mix, and chunk upload, along with the camera and peer connections.
9. Join a new meeting, stop the API, and restart it. Local media stops when the page detects the socket loss. Resume cannot restore presence cleared by API restart: a resume against missing presence shows **The live room reset. Join again.** If the API stays unavailable through the local recovery budget, the page shows **The connection was gone too long. Join again.** The catalog room stays `LIVE`; explicitly prepare devices and join again.

The stage is a full mesh of at most four people, counting the host and speakers together. Attendees stay outside that mesh. The live broadcast is one 720p HLS rendition, and the glass-to-glass delay is about 8–20 seconds. Use current Chrome or Edge on Windows. On one machine, STUN with local loopback normally produces ICE type `host`. TURN is optional and is used only when `TURN_URL`, `TURN_USERNAME`, and `TURN_CREDENTIAL` are set together. `FFMPEG_PATH` defaults to `ffmpeg`. If that binary cannot start, the broadcast becomes `FAILED`, the host sees `FFmpeg is not available. The stage is still up.`, the mesh stays usable, and the attendee sees the error with no player. When an API process becomes the owner of a Redis namespace, it marks every `STARTING`, `LIVE`, or `STOPPING` broadcast `FAILED` with `api restarted` and clears that namespace's live keys. `READY` broadcasts and their playlist files stay, and catalog room rows stay. Each attempt keeps its HLS playlist and segments under `DATA_ROOT` (default `apps/api/data`). Files remain until the registered owner deletes that finished attempt; there is no automatic retention cleanup. A second start while one broadcast is active returns `A broadcast is already active.`

A joined stage member can change camera, microphone, and speaker without leaving. Mute and a host lock apply to the replacement. A camera chosen during screen share is restored when the share stops. A lost camera or microphone mutes that input and waits for a deliberate choice. Speaker selection uses `setSinkId` where the browser provides it, including a later stage tile, the attendee broadcast, and the replay. The saved value is that output id for this tab. An unsupported browser keeps the default speaker. Attendees do not grant capture permission unless promoted. Starting stage media still requires both camera and microphone permission.

Live joins outside the waiting room, and resumes, refresh the devices the browser already allows, including attendee speaker choices, without requesting capture or extra permissions for labels. If enumeration is unavailable, system default remains available. If a new playback element rejects the saved speaker, the selector and saved choice reset to system default and the player shows the output error. A failed explicit speaker change keeps the previous choice when it can be restored; otherwise it resets to default and reports the failure.

An unexpected signaling-socket drop for a live member with a resume credential reserves the same membership for **20 seconds after the server detects the loss**. The participant id, role, host locks, join order, and raised hand stay. A suspended stage member still counts toward four; a host can demote a suspended speaker to free that slot. The page shows **Reconnecting. This room is still open.** as soon as it detects loss, and stops its camera, microphone, screen share, peers, analysers, demos, and upload producer. It opens fresh sockets at 0, 1, 2, and 4 seconds from local detection and starts no attempt at or after 20 seconds. A busy server, a temporary room failure, rate limiting, or an old transport that is still marked connected keeps that schedule and shows the condition. Losing a generation race does not make this page the owner of the other socket. Invalid credentials, expiry, a missing membership, and an ended room stop the attempts. Server and page detection can occur at different times. Old SDP, ICE, media, and moderation commands are discarded. An ICE/media failure while the signaling socket stays connected does not trigger this recovery.

Resume is limited to the same live page and a valid guest or host JWT. Its credential stays in page memory, outside `sessionStorage` and `localStorage`. Success restores the membership from a fresh snapshot and creates new peers only between connected stage members. Microphone and camera stay off until an explicit device action; host locks still block the matching device. Screen sharing stays off, demos stay stopped until **Spawn demo peer**, and a broadcast does not restart automatically. Attendees resume with no capture request and no WebRTC peer connection.

Explicit **Leave room**, page hide, navigation, and component disposal cancel recovery and discard the credential. A lost or unsent leave during tab close can hold the slot until grace expiry. Refresh, browser restart, token expiry, API restart, Redis presence reset, and another device do not resume the old membership. A fresh page with the same user but no credential receives **This guest is already in the room.** while the reservation remains. Grace expiry frees the reserved slot. In a live room, a delivered host leave or host grace expiry ends the catalog room.

Unexpected host loss fails the current broadcast with `Host connection lost.`, rejects later chunks with `broadcast_not_active`, and keeps the catalog room `LIVE` until host grace expiry or a delivered host leave. After resume, the host can use **Start broadcast** to create a new attempt. A suspended non-host is removed from the compositor inputs while the current broadcast continues. Explicit host leave still uses the graceful stop path; a clean stop can become `READY`. API restart still clears presence and fails in-flight broadcasts with `api restarted`.

Room chat is one plain-text channel for connected hosts, speakers, attendees, and waiters in both meetings and webinars. The panel appears after join and shows each accepted message once, in server order, with the sender's name and role at acceptance. Enter sends; Shift+Enter inserts a newline. Text and URLs stay literal text. An arrival preserves focus and, when you are reading earlier lines, shows a new-message count instead of scrolling to the bottom. Demo peers generate no chat lines.

| Chat limit                | Shipped behavior                                                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Text                      | 1 to 1,000 UTF-16 code units after trim and at most 4,000 UTF-8 bytes; some emoji use two code units                                     |
| Retained history          | At most 500 recent messages per room in Redis; the oldest messages are dropped                                                           |
| Idle expiry               | 86,400 seconds (24 hours), refreshed by chat writes                                                                                      |
| History pages             | Latest 50 messages by default, in ascending sequence; requests allow 1 to 100 per page                                                   |
| Participant rate          | 10 accepted messages per participant per 10 seconds                                                                                      |
| Room rate                 | 100 accepted messages per room per 10 seconds                                                                                            |
| Pending sends             | At most 5 waiting for an acknowledgement; a sixth stays in the composer with a busy message                                              |
| Unsent attempts           | At most 20 pending or failed attempts and 40,000 UTF-8 text bytes per page; a draft that would exceed either limit stays in the composer |
| Retry deduplication       | Latest 500 participant/request-id pairs per room; an accepted duplicate spends no rate and returns the original message                  |
| Participant-rate capacity | At most 1,000 fields per room; a new field past the cap returns `chat_busy` without evicting an existing field                           |
| Chat work queue           | At most 32 waiting operations per room, separate from stage work; excess returns `chat_busy`                                             |

**Pause chat** blocks every new message, including the host's and a synthetic participant's. Everyone sees **The host paused chat.** Accepted lines remain readable. **Resume chat** permits new sends again. Join and socket resume fetch recent history. During recovery the panel is read only; in-flight sends become **Not sent**, and the page does not send them again automatically. **Retry** uses the original request id; **Dismiss** removes the failure without sending it. A retry after its dedup entry has fallen outside the latest 500 pairs can create another message. A gap lost to retention shows **Earlier messages are no longer available.** Chat events also use the existing socket event budget. A rejected, busy, or rate-limited send stays on chat and leaves the stage, peer connections, and broadcast running.

When adding a draft would exceed the unsent-attempt count or text-byte limit, **Send** is disabled and the panel asks you to retry or dismiss a message. Enter keeps the draft too. Pending and failed attempts stay until acknowledged or explicitly dismissed; the page does not evict them to make space. Same-id **Retry** remains available at the retention limit, within the five-pending-send limit. Successful acknowledgement or **Dismiss** frees space. Reconnecting keeps the retained attempts and draft without sending them automatically.

The panel states **Chat is live. It is not synced to the delayed video.** Room end disables both the composer and Retry, keeps the lines already on the current page, and shows **This room has ended. Chat is closed.** Shutdown deletes the room's chat keys, and API startup clears chat with live presence. Chat is temporary Redis state: no messages are stored in the PostgreSQL catalog or attached to a replay. Each accepted line shows the server time after the role, as specified in [V2 Phase 5 Section 5.1](plans/V2/phase5.md). The visible text is the local hour and minute from `sentAt`, and it includes the date when that local day differs from now. The value on the wire stays the server instant.

The **Questions** panel lets connected hosts, speakers, and attendees ask a plain-text question and upvote each question once. It appears after join, including for the pre-start host. Waiters and demo peers cannot use questions. The server supplies the author's membership name; question text and angle brackets stay literal. The host role, including a guest host, supplies **Dismiss**, **Feature**, **Clear feature**, **Close questions**, and **Open questions**. Dismiss frees a board slot and clears a matching feature. Closing blocks everyone's new questions, including the host's, while voting and host moderation remain available.

| Question limit            | Shipped behavior                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Text                      | One line, 1 to 200 UTF-16 code units after trim and at most 1,000 UTF-8 bytes; ASCII controls are rejected    |
| Retained board            | At most 100 questions per room; dismiss frees a slot without reusing an id                                    |
| Submit rate               | 5 new questions per participant and 30 per room per 10 seconds                                                |
| Vote rate                 | 20 new votes per participant and 100 per room per 10 seconds; repeat votes do not increment or spend the rate |
| Participant-rate capacity | At most 1,000 fields in each separate submit/vote rate hash; excess returns `qa_busy`                         |

Local `pnpm dev` does not force-kill the API as its first step. The supervisor compiles with `nest build --watch` and runs the API separately. Nest's own `start --watch` path on Windows uses `taskkill /T /F`, which skips shutdown and leaves the owner guard behind, so a shared-package rebuild and a successful API compile both ask the running API to close through a private channel instead. That channel is a named pipe on Windows, or a socket under the temp directory on other systems. It is not an HTTP route and it is not bound to a public address. The API opens it before acquiring the owner guard. The supervisor waits up to 15 seconds for that process and its child processes to exit, which lets Nest close FFmpeg's input and release only this process's guard. If the close misses the deadline, the supervisor force-stops the tree and prints that the guard may still be held. It does not delete the guard, and it does not start a replacement owner. Use the manual recovery steps below after that forced stop, a crash, or Redis loss. A routine graceful dev restart does not need them.

An unexpected API exit stops the supervisor's compiler and web children, releases its shared watcher or follower, and preserves the API exit code (a signal exits with code 1). API, compiler, and web spawn failures use the same cleanup and exit with code 1. A shared follower leaves the external writer running. Normal watch restarts keep the supervisor active, and repeated stop requests wait for the same complete cleanup.

Network and socket admission is process-local and configurable. Those rate counters have fixed windows (`RATE_WINDOW_MS=60000`) and at most `RATE_KEYS_MAX=10000` identities each. A full counter map rejects new identities until entries expire; it never evicts active counters to admit another identity. HTTP admission runs before JSON parsing and controllers, returns 429 with `rate_limited` and `Retry-After` set to the remaining whole seconds of the window that rejected the request, and leaves GET health probes available. HLS reads and chunk uploads use separate counters, so playback on a shared address cannot spend the host upload allowance. CORS runs before admission so allowed browser clients can read those errors. Guest issuance, register, login, promote, password change, and Google start/callback/ticket/link share `GUEST_RATE_LIMIT` after the ordinary control budget. Google actions spend that budget for every method, including preflights; the Google probe spends only the ordinary control budget. Guest creation and Google code exchange have separate in-flight counters, each capped by `GUEST_PENDING_LIMIT`. Register, login, promotion, and password change do not use that cap. Their bcrypt cost stays 12 and runs on a bounded worker-thread pool (`PASSWORD_WORKER_LIMIT`, clamped to this machine's available parallelism) with a waiting queue (`PASSWORD_QUEUE_LIMIT`). A full pool returns `server_busy` and does not retain the rejected password. Each email, and each signed-in user, also has `PASSWORD_ACCOUNT_LIMIT` attempts per rate window. The window expires, so this is not a permanent lockout, and a limited email gets the same response whether or not it is registered. Admitted password attempts stay occupied until they settle, even after the request disconnects. These defaults are a small pre-measurement ceiling; repeat the latency check on the target VPS before raising them. Google exchange keeps its own cap and does not run password workers. Socket authentication is bounded before user lookup, and command rates are counted by verified user ID across sockets, including invalid payloads. Rejected commands receive `rate_limited` or `server_busy` before queueing; `room:leave` bypasses command rates. The command loads `.env` without replacing explicit environment overrides. `DATABASE_URL` must permit CREATE DATABASE and connect to the created database. The harness creates a random `sf_broadcast_<uuid>` database, runs the compiled migrations (then verifies a second run is empty), and boots the compiled Nest `main` on random loopback ports. It issues a real guest token via HTTP, joins through Socket.IO, starts a webinar broadcast, and posts valid generated VP8/Opus WebM chunks with a duplicate retry. It stops through the gateway, checks READY, fetches the authenticated playlist/segments, verifies ENDLIST, and decodes H.264/AAC output including dimensions and duration. Independent runs check startup recovery of STARTING/LIVE/STOPPING rows while preserving READY/media and a foreign Redis namespace, and a missing FFmpeg binary while stage commands remain usable.

The broadcast integration uses a unique Redis namespace and OS temp media directory, graceful API shutdown through its private local channel, bounded request/process waits, and process-tree cleanup as a fallback. It drops only the database it created, deletes only its random Redis keys and sentinel, and removes only its owned temp directory; it does not migrate the database named in your environment, reset live presence, or restart containers. CI supplies disposable service infrastructure. The pinned CI binary comes from [ffmpeg-static release b6.0](https://github.com/eugeneware/ffmpeg-static/releases/tag/b6.0); local binaries may differ and their version is always logged. This provides automated encoding/persistence/bootstrap evidence; browser playback, native recorder behavior, and physical-device acceptance still require their recorded observations.
